# Classification qualification — 2026-10-01

Scope: changes on `codex/classification-reliability`, based on preview main
`ed60ce087472d8d0868d6849343b6c7935ea07b9`. No merge, signed release or
physical-device qualification was performed. Reproduction commands and source
pins are in [README.md](README.md).

## Findings and reproduction

1. **Mixed search depths could manufacture a unique-best gap.** A probe against
   the base source fed depth-12 scores `[0, -10]`, then only the depth-13 primary
   score `300`. The old collector combined `[300, -10]` and classified Qa3 as
   Brilliant. The new collector retains the completed `[0, -10]` pair. This
   reproduces the defect class; the original phone's UCI stream was not captured,
   so it does not prove that exact stream caused the screenshot.
2. **Engine hash reuse changed later Fast results.** In SF18's
   Fast→Thorough→Fast sequence with the old warm-run policy, 76 of 83 positions
   changed scores/PVs and four move labels changed (plies 9, 23, 29, 31).
   Resetting between runs produced zero score/PV or label differences in this
   experiment. Production now resets each full-game run and uses one thread;
   it retains a warm hash between positions within a run.
3. **Fast evidence needs a confidence check.** Raw EC rules can award a standout
   label from a gap that appears only in the last iteration. Fast now requires
   agreement between completed iterations or an independent confirmation.
   Only actual provisional `!`/`!!` awards consume the cap of three pairs.
   Deterministic material values are reused between the two owned workers.
4. **Cancellation could be reported as an engine fault.** A very early stop may
   return only `bestmove` or bounded scores. New tests failed against the
   intermediate implementation, then passed after cancellation was handled
   before demanding a scored PV. The next search reuses the healthy engine.
5. **The translated capture search missed upstream's mate value.** It now
   applies `-10000` at checkmated capture-search nodes. Terminal root handling
   remains an explicitly documented app difference.

The Android test uses the shipped `multistockfish_light` 0.1.0 native package,
not the desktop SF18 executable. On the API 36 ARM64 emulator (2 cores, 3 GB),
the final sequence took **2.631s Fast, 28.240s Thorough, 2.144s Fast**, including
classification. Both Fast runs produced identical labels and Brilliant at
plies **22, 34, 38**, never at Qa3 (23). Thorough's minor labels differed from
Fast, as the search budgets differ.

An isolated final desktop SF18 run took **3.265s engine search + 0.501s
provisional material/classification + 0.325s confirmation**, **4.112s total**.
These are observations, not latency guarantees or phone benchmarks. Another
successful run under concurrent test load took 8.720s. The confirmation cap is
at most 3s of *requested engine search time*, not a cap on total analysis time.

The normal CI workflow automatically picks up the new deterministic Flutter
tests. It does not build Rust, run native benchmarks or download chess games.
The reference fixtures add approximately 0.65 MB; the focused 32-test reference,
session, confidence and cancellation run took about five seconds on this host.

## Failed qualification attempts and limits

- Debug Android runs were inconsistent: one retained all three Black
  brilliancies, another withheld Na4. In the failing run, the critical search
  reached only depth 10 instead of 12 before Fast's time limit. Neither awarded
  Qa3 Brilliant. This is evidence that low search effort can still miss awards.
- The initial profile attempt had the same problem because Flutter's plugin
  profile variant packaged the exact Debug native library. Its ARM64 Light
  SHA-256 was `f6f12c369231447d9027a4600cff122978bbe4ed863fd8f321abc0cc5c429006`.
  That attempt was stopped after identifying the configuration issue. The root
  Gradle profile override now uses CMake Release; two complete optimized
  sequences passed. The final optimized packaged ARM64 library's SHA-256 was
  `850aa1f54cfa507c28e14d2931a0b2875818455959e2080771bceabfd98ff4d2`.
- A two-thread Light experiment also changed labels, including a raw-rule Qa3
  Brilliant in Thorough. Identical annotation rules do not imply identical
  labels with different engine versions, thread counts or time budgets.
- The system Python lacked an optional dependency; rerunning in the documented
  hardening venv passed all 31 tests. No dependency was added to the app.
- The conservative Fast rule intentionally withholds weak `!`/`!!` labels.
  It cannot prove chess truth or guarantee no false positive at every depth.
  Difficult material searches can still take seconds, but run in cancellable
  workers; no arbitrary node cutoff replaces the upstream material algorithm.
- This is Dev-flavor native/runtime qualification, not a signed Preview/79M
  release APK audit. Repeat the documented real-phone and release-packaging
  checks before publication. No physical board testing is claimed.

The optional harnesses, fixtures and reference sources are committed so future
changes can repeat this work. Audit-created APKs, native/Dart build output,
materialized model copies and downloaded Rust toolchains were removed, and the
audit emulator was stopped without saving a snapshot. Compact logs and traces
were retained locally. Shared SDKs and other worktrees' artifacts were untouched.
